# nxnative on Android

The Android port of the host: one launcher APK (`android/app`) that holds the host, one per game it runs (`libnxhost_<title ID>.so`, built from `android/host`), and no game code, and a pack per game, made from the user's own dump: by the app itself on the phone (**Prepare**, ONDEVICE.md), or on the Mac and copied to the phone beside the game folder. This build boots a game's CPU side and replays its NVN clears, copies and presents on Vulkan (draws are not on Vulkan yet), plays its sound through AAudio, decodes its movies with `AMediaCodec` and takes gamepads, touch and phone motion; a graphics self-test checks the Vulkan path without a game. [PORTING.md](PORTING.md) has the design, the status and the next pieces; [TESTING.md](TESTING.md) the steps on a phone. [FRONTENDS.md](FRONTENDS.md) says how emulator frontends (ES-DE, Daijisho, Pegasus…) start a game.

| Folder | What |
|---|---|
| `android/host` | CMake build of `libnxhost.so` for arm64-v8a, API 33+ (`GAME=<title ID>` picks the profile; `NX_GAMES=<id>,<id>,…` builds `libnxhost_<id>.so` for each, as the APK does) |
| `android/app` | the launcher: Gradle + CMake, Java, `dev.nxnative.android`, named "Banana Native test" (`-PnxPlay=true`: `dev.nxnative.android.play`, "Banana Native") |
| `scripts/pack_android.py` | the packer (the Mac's, and the app's own: the same tools run in the app, ONDEVICE.md) |
| `android/ondevice` | the app's packer, native side: embedded CPython (`libnxpack.so`), and `build.sh`, which makes the stage the APK takes |

**License.** nxnative is MIT. The Android build includes Lossless Scaling frame generation ported from Eden ([`dm/gfx/vk_android/lsfg`](../dm/gfx/vk_android/lsfg/LICENSE.md)), which is GPL-3.0-or-later: **an APK built with it (the default) is GPL-3.0-or-later as a whole**; `-PnxLsfg=false` builds one without it. See [NOTICE.md](NOTICE.md). `Lossless.dll` is never in the repository or the APK.

## The environment

The packer runs the rewriter, which needs Capstone 5, lz4 and, on a PC or Mac, zbic from PyPI (the ZBIC segments of system 22.0.0+ modules, as The Legend of Zelda: Ocarina of Time (`0400486024DEC000`) has; the APK carries its own decoder, [libzbicdec](../dm/third_party/zstd-zbic/README.md), instead; `pyproject.toml`, dependency group `android-pack`). Keep the environment on the dump drive, not in the home folder:

```sh
micromamba create -p <dump folder>/.venv-nxnative python=3.12 -c conda-forge
<dump folder>/.venv-nxnative/bin/python -m pip install "capstone>=5,<6" lz4 zbic==1.0.1.post1
```

Capstone comes from pip: conda-forge's Capstone 5 finds its library only through `CONDA_PREFIX`, so it fails when the environment's Python is run without activating it.

### The launcher and the window

`scripts/bananative.command` (macOS) and `scripts/bananative.bat` (Windows, through `bananative.ps1`) make the environment ready without any of the above: they use `BANANATIVE_ENV`, the environment remembered in `.bananative-env` (not committed), an active conda environment or a micromamba / conda environment named `bananative*`, the first whose tools pass `scripts/bananative_env.py` (Python 3.14, Capstone 5, lz4, zbic, zstd, Tk, `spirv-val`, the translator under .NET 10). With none, they make one from `android/environment.yml` in `<folder>/bananative/` (asked once; micromamba is downloaded there when none is on PATH, and its package caches stay there); one of theirs that lacks a tool is remade. An environment made before zbic was in `android/environment.yml` (before 0.2.2) only needs it added: `<environment>/bin/python -m pip install zbic==1.0.1.post1` (Windows: `<environment>\python.exe -m pip install zbic==1.0.1.post1`). `android/environment.yml` carries the .NET runtime (conda-forge `dotnet-runtime`), so no system .NET is needed: the launchers and `bananative_env.apply()` set `DOTNET_ROOT` to the environment's.

| Command | What |
|---|---|
| `scripts/bananative.command` | the window, `scripts/pack_gui.py`: pick a `.nup` file or a dump folder, its versions and DLC, the tool check, **Prepare** with a progress bar (the rewrite, `shader_split.py`'s `progress:` lines, `vk_android_build.py`'s `progress` lines) and the log; **Stop** ends the packer and its subprocesses, and the next run resumes |
| `scripts/bananative.command pack <game> [...]` | `pack_android.py` with the environment's Python and tools |
| `scripts/bananative.command check` | the tool check |
| `scripts/bananative.command setup [<folder>]` | make (or remake) the environment in `<folder>/bananative/` |
| `scripts/bananative.command python [...]` | the environment's Python, set up as for the packer |

The window runs `pack_android.py` as a subprocess with the options it shows (the first log line is the command), so both make the same pack. The Windows launcher and the window's Windows parts have not run on Windows yet.

## Pack a game

```sh
<dump folder>/.venv-nxnative/bin/python scripts/pack_android.py <dump folder>/<game folder>
```

The game folder has the layout `scripts/pack_dump.py` reads (`base/exefs`, `base/romfs`, `updates/<version>/`, `dlc/<DLC title ID>/<n>/romfs`), and the game needs a profile in `dm/games`. The packer rewrites the profile's modules of the newest version (`--version N` for another) with `patch_nso.py --target android` into `<game folder>/../<title ID>-work/android-pack/` (`--out` for another folder) and leaves the RomFS out. A repeat run keeps the modules whose inputs did not change; Prepare skips what is already current (code rewrite is a few minutes when keys change, and existing shaders from the cache or library are reused).

It also puts the game's shader library in the pack ([SHADERS.md](SHADERS.md)): the library of this source tree's version, `v-<DMSH_VK_CHAIN>` (`dm/gfx/nvn/dmsh_chain_vk.h`). One in the shader cache, `<title ID>-work/android-shaders/lib/v-<V>/` (`--shader-cache` for another folder of `v-<V>/` libraries), is copied when its `inputs.tsv` names this game and its profile's current inputs; otherwise the packer builds it there from the Switch shader package, `<title ID>-work/android-shaders/pkg` (`--shader-pkg`; `shader_split.py`'s output, the folder `dmsh_build.py` takes), with `vk_android_build.py` (about 10 minutes for DKB with `-J 12`). The build needs Python 3.14 (or `backports.zstd`), the .NET 10 runtime and `spirv-val`; the packer runs it as a subprocess with the first of `python3.14` / `python3` that has zstd (`--shader-python` names another). With neither a library nor a package the pack is made without shaders and a `[RED]` line says so; `--no-shaders` leaves them out on purpose. Libraries of other versions in the pack's `shaders/` are kept (another APK may load one; delete them by hand to save the space). Each module is rewritten into `<pack>/.rewrite-<module>/` and moved in when complete, its `<module>.android.key` last: a module without its key is unfinished, and the launcher refuses it. The key hashes the rewriter's files (`REWRITER`), the module, the profile's `patches.py` and `game.tsv`'s `build` rows (the only rows the rewriter reads; an older key made with the whole `game.tsv` still counts when the pack's own copy has the same `build` rows: [packing.md](../docs/reference/packing.md)); a key made with an earlier rewriter file kept in `dm/tools/rewriter_equiv/<file>.<commit>` counts as current, both for the packer (the module is kept) and for the launcher (`RewriteKey`, no "other tools" chip). A file goes there only when the rewrite output with it was verified byte-identical to the current file's on each game (`patch_nso.py.b4269ab15768`: 10767b45 only clears the spin search's decode cache per head; MKW and DKB main identical. `patch_nso.py.10767b45d33d`: the Windows changes of [Packing on Windows](#packing-on-windows), which leave the Mac's path as it was; DKB main and sdk and MKW main identical, also with the Windows path forced). Tests: `dm/tools/tests/test_android_rewritekey.py`.

| File in the pack | What |
|---|---|
| `<module>.patched.bin`, `.fixups.tsv`, `.gates.tsv`, `.sites.tsv`, `.changed.tsv`, `.cuts.tsv`, `.obs.tsv` | the rewritten module and its tables, as the Mac host loads them (`fixups.tsv` says `TARGET_ANDROID 1`) |
| `pack.tsv` | format, title ID, name, version, modules and their build IDs, the RomFS folder and each DLC's folder relative to the game folder, `shaders` (the library's path in the pack, when it has one), the packer's commit |
| `shaders/v-<DMSH_VK_CHAIN>/dmsh_vk.lib`, `inputs.tsv` | the shader library for the Vulkan replay (SPIR-V, zstd; about 350 MB for DKB) and its stamp (game and profile inputs) |
| `game.tsv` | the profile (the host has it compiled in; kept for reference) |
| `rewrite_<module>.log`, `<module>.android.key`, `build_src.sha256` | the rewriter's output and what a repeat run compares |

Packs are made from the user's own dumps for the user's own phone: they never go into the repository or anywhere public.

### Packing on Windows

The packer runs on Windows (x64) as on the Mac, from a dump folder or a `.nup` file, and is made to write the Mac's pack byte for byte (the Windows paths were checked on the Mac; a run on Windows itself is still to come). `scripts\bananative.bat` makes the environment and opens the window ([The launcher and the window](#the-launcher-and-the-window)); by hand, with micromamba on the dump drive (conda-forge has Python 3.14, SPIRV-Tools and the .NET 10 runtime for win-64):

```bat
micromamba create -p <dump drive>\bananative-env -f android\environment.yml
<dump drive>\bananative-env\python.exe scripts\pack_android.py <dump folder or .nup file>
```

- **The checkout.** The rewrite key and the shader versions hash the repository's files byte for byte, so the checkout must hold the Mac's bytes: `.gitattributes` turns Git's line-end conversion off (Git for Windows converts to CR LF by default). A checkout made with the conversion on (before that line) needs a fresh clone.
- **The translator.** `dmsh_xlate_bin/dmsh_xlate` is the Mac's apphost; its dlls are portable. On Windows the tools start `dotnet dmsh_xlate.dll` (`tool_lock.py` `xlate_command`; a `dmsh_xlate.exe` beside it is taken first), with `dotnet` from `DOTNET_ROOT` (the launchers point it at the environment's `dotnet`) or `PATH`. The lock still checks the same dlls.
- **The shader build** runs as `dm/gfx/tools/vk_android_win.py`, which runs `vk_android_build.py` unchanged (it is one of `DMSH_VK_CHAIN`'s files) with four things Windows needs put around it: the translator's command, `spirv-val`'s temporary files opened so that another program can read them, text files written with `\n` in UTF-8, and binary package reads (`os.open` with `O_BINARY` and a locked `os.pread`). `--shader-python` defaults to the packer's own Python; `spirv-val` comes with the environment (its `Library\bin`, which the packer puts first on its tools' `PATH`, so the environment need not be activated).
- **The rewriter** works through its pieces in one process (`patch_nso.py` `in_parallel`: Windows cannot fork, and a spawned worker would run the whole script): about 30 s for DKB's main instead of 13 s with forked workers. Every text file it writes is `\n` and UTF-8, and the tools the packer starts get `PYTHONUTF8=1`.
- **Stopping.** The packer puts itself and every tool it starts in a Windows job that ends them all when it ends, so a stop is `TerminateProcess` on the packer alone (Python's `Popen.terminate()`); a pack stopped at any point is safe, as on the Mac. `CTRL_BREAK_EVENT` (a packer started with `CREATE_NEW_PROCESS_GROUP` by a program that shares its console) stops it as Ctrl-C does.

## Build the APK

```sh
android/ondevice/build.sh <work dir>                                   # once (and after a change to dm_pack.c, the translator or the pins): <work dir>/stage
cd android/app && ./gradlew -PnxPackStage=<work dir>/stage apk         # → android/app/out/nxnative-android.apk
```

Every APK carries the packer that prepares a game on the phone (ONDEVICE.md, In the APK): CPython 3.14 and the repository's tools, the translator and SPIRV-Tools; `-PnxPackStage` (or `NX_PACK_STAGE` in the environment) names the stage `android/ondevice/build.sh` makes, and Gradle stops and says what to run without it. `-PnxPackEngine=fake` builds a simulated packer instead, for work on the screens (its packs are placeholders that never start). Size (2026-11-03): 23.8 MB, of which the packer is 20.9 MB (`libpython3.14.so` 5.8, `python.zip` 6.0, `libdmsh_xlate.so` 4.2, SPIRV-Tools 2.75, `tools.zip` 2.1, `libnxpack.so` 0.01, all stored); without it the APK was 2.8 MB.

**Games in the APK.** The host has its game profile compiled in (`game_profile.h`, as `dm/host/Makefile`'s `GAME`), so the APK carries one host per game: `-PnxGames=<title ID>,<title ID>,…` (default `nxGames` in `gradle.properties`: every game supported on Android, the profiles whose `readiness.tsv` has a `status` row, so a build made without `-PnxGames` never lacks one, `dm/tools/tests/test_android_games.py`; the first, `040074A01BF12000`, Donkey Kong Bananza, is the default game) builds `libnxhost_<title ID>.so` and its JNI shim `libnxlaunch_<title ID>.so` for each (`android/app/src/main/cpp/CMakeLists.txt`, `nxhost_add` in `android/host/CMakeLists.txt`), puts each profile in the packer's `tools.zip`, and hands the launcher each game's name, builds, shader count and shader inputs digest (`BuildConfig.NX_PROFILES`, read by `Profile.java`). The game's process loads only its own pair (`Native.load`); the self-test loads the first game's. Each game added compiles the host once more (about the same time again). A game whose profile is not in the APK is refused with one sentence (`Profile.missing`: "This app version does not include <game> (<title ID>). Install a build that includes it."), when it is added, prepared, resumed or started, and its card offers no Prepare, Retry or Play (a Prepare job an APK with the profile left behind is refused by the service too: ONDEVICE.md); nothing crashes. A provisional profile made by the NSP script on the Mac (`DM_GAMES_DIR`) is not in `dm/games`, so an APK cannot be built with it yet. `-PnxApp=<suffix>` makes it another test app, `dev.nxnative.android.<suffix>` (label `Banana Native <suffix>`, or `-PnxLabel=`), into `out/nxnative-android-<suffix>.apk`: a game in bring-up (`-PnxGames=0400C3F00006E000 -PnxApp=mkw`) installs beside the test app without replacing it. Its env.txt, logs, saves and packs are in `/sdcard/Android/data/dev.nxnative.android.<suffix>/files/`; `-PnxPlay=true` builds the play app (`dev.nxnative.android.play`). The APK is signed with the debug key, debuggable, minSdk 33, arm64-v8a only, and its native libraries are stored uncompressed and aligned for 16 KB pages. Gradle needs `android/app/local.properties` with `sdk.dir=` (Android Studio writes it) and NDK 28.2.13676358.

## The launcher

- **Icon and background**: the icon is an original banana drawn as vector paths with a small happy face (`res/drawable/ic_banana_happy.xml`, the face of Home's header; the plain banana is `ic_banana.xml`; no game art), an adaptive icon (`mipmap-anydpi-v26/ic_launcher` and `ic_launcher_round`: green background, the happy banana in front, inside the safe zone, and its silhouette with the face cut out for themed icons, `ic_banana_happy_mono.xml`; `drawable/ic_launcher` is the legacy one). The test app's icon has a red-orange "T" dot at the lower right, the play app's has none: `build.gradle` adds `src/variant-test/res` or, with `-PnxPlay=true`, `src/variant-play/res`, which hold `ic_launcher_badge*.xml`. Behind the main screen, `BananaBackgroundView` tiles the same banana faintly in a tilted diagonal grid that drifts slowly and wraps seamlessly; it animates (Choreographer, at most about 60 redraws a second) only while the main screen is resumed, so never while a game runs, and stays still when the system's animations are off (animator duration scale 0).
- **Two pages** (`MainActivity`): **Home**, the path to playing, and **Settings** (the gear in Home's header; Back returns): Updates (first), the defaults of every game (overlay, resolution, frame rate cap, frame generation), GPU driver, Folders, the Readiness check, the graphics self-test, Share log, ADB control (debug; play and release apps only: [TESTING.md](TESTING.md#adb-control)), and About (the build tag, the APK's title IDs, credits). Home shows the All files access card while it is missing, the game being prepared, and the games; with none, one card with the three steps (pick dump, prepare, play) and **Add game**. A dump of a title the APK has no profile for is refused with its title ID (`Profile.missing`); Settings › About lists the games this app includes. A dump of a build the profile does not list is refused with what it holds and what the app supports, and **Try anyway** prepares it untested (ONDEVICE.md). Messages keep file paths, build IDs and a tool's output under a closed **Details** (selectable, with Copy), the main text short: what happened and what to do. The launcher adds no game names of its own: a game shows the name its pack carries, the Readiness check the added game's name or its title ID.
- **Updates** (`Updater`, `UpdateCheck`; release app `dev.bananative.android` only): once per app start (a new process, `MainActivity.onCreate`; not on a resume or a rotation), Home asks every release source at once (`UpdateCheck.SOURCES`, in order): GitHub, `https://api.github.com/repos/moceure/BananaNative/releases?per_page=10` (the list: every release is a pre-release, which `/releases/latest` skips), then the Forgejo mirror, `https://git.eden-emu.dev/api/v1/repos/moceure/BananaNative/releases?limit=10` (the same releases; added when GitHub suspended the moceure account on 2026-11-08, so the app keeps finding updates while either host is unreachable). No token, User-Agent `BananaNative-updater`, 6 s to connect and 8 s to read; each list is asked through its URL with a fresh query parameter (`&_=<time>`, `UpdateCheck.busted`) and `Cache-Control: no-cache`, so a shared cache in front of a host cannot answer with an old list (one in front of git.eden-emu.dev served a two-hour-old list after v0.2.3: [the entry](../docs/reference/packing.md#the-app-says-up-to-date-though-a-newer-release-is-on-giteden-emudev)). Both APIs give the same fields (`tag_name`, `draft`, `prerelease`, `body`, `assets[]` with `name`, `size`, `browser_download_url`; only GitHub gives a `digest`); `Json` reads them. A source that fails (no network, an HTTP error, a timeout, an unreadable answer) is left out with a log line. From all the answers the updater skips drafts and tags that are not `vX.Y.Z` and takes the highest version above the app's `versionName` that has an `.apk` asset (on a tie, the earlier source), so a source that is down or behind never hides a newer release. The APK link must be https on that source's own hosts (GitHub's releases: `github.com`, `objects.githubusercontent.com`; Forgejo's: `git.eden-emu.dev`); a release whose APK is elsewhere is skipped. A popup shows the version, the release notes (the release body's Markdown as styled text: headings, bold, italic, code, lists, links; `ReleaseNotes`; scrolling when long) the size and where it is from (`from GitHub`, `from git.eden-emu.dev`), with **Update** and **Later**; it comes back at every fresh start while a newer release exists. Update downloads the asset through its own `browser_download_url` (so the source counts the download; nothing is mirrored) into the cache's `updates/` with a progress dialog, checks the size and, when the API gives a `digest`, its SHA-256 (a file that fails is deleted, never installed), and installs it with `PackageInstaller` (a session limited to this package; Android refuses an update signed with another certificate, and asks the player to confirm). When installs from this app are not allowed, the launcher opens Android's **Install unknown apps** screen and continues on return. Old downloads are deleted at the next start. A check where every source fails shows nothing (Check for updates says why, per source); logcat tag `nxupdate` says why. Installed apps up to v0.2.0 ask only GitHub: they need one manual install of a release with both sources. Settings › **Updates**, the first section: **Check for updates** (the row shows `Banana Native <version>`) checks at once: the popup, or "You're up to date (vX.Y.Z)". There is no switch: the release app always checks at a fresh start. Test apps do not check, unless `Android/data/<app>/files/update.txt` has `repo=<owner/name>` (GitHub), `forgejo=<owner/name>` (git.eden-emu.dev) or `url=<https URL of a releases list in the APIs' JSON; its APK on that host or GitHub's>` (the sources named are asked, in that order), with `version=<X.Y.Z>` for the version the app takes as its own (a test app's `versionName` is not one). Tests: `python3 dm/tools/tests/test_android_update.py` (`UpdateCheckJvmTest`: versions, release picking, digests, the notes' Markdown, also on the real v0.1.3 body; the sources: both APIs' JSON, also a recorded Forgejo answer, the newest across sources, a failing source, the asset host allow-list).
- **Game list** (`MainActivity`): every added game has a card (its initial, name, a state: Ready, Shaders needed, Needs preparing, …, one big button and ⋯ (or a long press), which opens the game's page: its name and **Play** in the header, then the tabs **Performance** (Game settings, below), **Saves** (Back up / Restore / Import save) and **Storage** (Prepare again, Export pack… / Import pack…, Folders; Add to home screen, Share log; the title ID and folders under a closed Details; Remove from list apart at the bottom)); the button is **Play**, or **Prepare** / **Prepare shaders** when the pack does not fit and the folder is a dump (it goes straight to Prepare, which asks first). **Add game** opens the Storage Access Framework picker for a game folder (a dump of any game the APK has a profile for: `base/`, `updates/`), a `.nup`, or a folder that holds games: then every game in it is added (each `.nup` in it and each dump subfolder with `base/exefs/main.npdm` or `exefs/main.npdm`, one level deep; not `<title ID>-work` or pack folders; `PackFind.gamesIn`), identified off the main thread, and one message says what was added, what this app cannot run (no profile in this APK) and what needs Prepare; a folder with one game is that game. The pack is looked for (`PackFind`, `Folders.find`) in the pack folder picked for that title (Folders), the app's storage (`Android/data/<app>/files/packs/<title ID>`, where Prepare and Import pack… put it), beside and inside the game as before (`<game folder>/../<title ID>-work/android-pack`), then in the folder holding the game and up to three folders above it, never above the storage volume's root: every `<dir>/<title ID>-work/<any name>/` with a `pack.tsv` (a Mac pack copied as `xlate2-pack`, `android-pack-1.8.0`, …) and `<dir>/android-pack`. Only packs of this title whose code fits the game (`PackCheck.blocking`: the dump's game build, a build this APK supports, finished code) count: one with this APK's shader library first, else one whose older library the automatic restamp or delta shader update brings current (the card then runs it, as after an APK update); within each, the picked folder, then the app's, then the nearest. Such a pack is used with no question. A dump with none goes to **Prepare** (one job at a time, any of the APK's games): the app makes the pack on the phone, or only what does not fit (Prepare skips what is already current: code rewrite is a few minutes when keys change, and existing shaders are reused; ONDEVICE.md, The app); its question also offers **Use an existing pack…** (the folder picker) and **Import pack…** (a `.zip` from Export pack… or a pack folder). From a folder of games, a dump with no usable pack gets a card whose button is Prepare instead (no job starts by itself). A one-version folder (`exefs/`, `romfs/`) without a pack gets the pack folder picker. A game card's state says Ready or what is wrong; a small **Pack from other tools** chip when the pack's code was made by other tools than the APK's, whose tap says what that means (it usually runs; ⋯ › **Prepare again** updates it). The picked trees are turned into `/storage/...` paths (`PathUtil`: `primary:` is the shared storage, another volume ID is `/storage/<ID>`), since the host opens files by path with All files access (`MANAGE_EXTERNAL_STORAGE`; Home shows a card with **Allow** while it is missing). Games are remembered in the app's preferences. Settings › **Share log** sends the newest log, a game's or the self-test's; a game's Manage sheet has its own **Share log** (that game's newest log). Settings › **Graphics self-test** opens `SelftestActivity` (TESTING.md, Test 2).
- **When the game stops unexpectedly** (`ExitWatch`, `ExitNotice`): back in the launcher after the game's process ended without Stop, a dialog says "The game stopped unexpectedly", the game's name and one plain sentence of cause (the app ran into an error; the game crashed; the GPU driver stopped responding; Android closed it because the phone ran out of memory, or because it stopped responding; it closed without saying why), with **Share log** (the log of that run) and **OK**, once per exit. `LogDigest` reads the last 2 MB of that log with `dm/tools/log_digest.py`'s rules (`dm/tools/log_rules.tsv` and `log_noise.tsv`, which the build copies into the APK's `assets/digest/`): when a line matches the rule of the tool's verdict, the dialog adds "Likely cause: …" and **What it means** (an in-app dialog that explains what happened and what to try in plain words with the technical cause below it, and **More details** to open the reference doc when available), and **Share log** also sends `<log name>.digest.txt`, the tool's verdict, crash, `[RED]` / error lines and rules sections for that log (`test_android_logdigest.py` checks they match the tool's). It comes from the run's exit record (`last-exit.txt` in the app's files: the uncaught-exception handler, `nxlaunch.c`'s signal handler, Stop), Android's exit reason for the `:game` process and the end of the run's log; a game that dies while Home shows is noticed within 2 s. An uncaught Java exception also goes into the run's log as `[RED] crash:` lines. The test app takes `DM_TEST_CRASH=java` or `=native` (env.txt) to try it ([the mechanism](../docs/reference/threads.md#the-games-process-ends-and-the-player-sees-nothing-android)).
- **A run** (`GameActivity`, in its own process `:game`): the host is started once per process and ends it. `nxhost_main("nxhost", <pack folder>)` runs on a native thread with an 8 MB stack that ART does not know, with `DM_ROMFS=<game folder>/<romfs from pack.tsv>`, `DM_SAVE`, `DM_TEMP` (`<external files>/temp/<title ID>`: the game's pipeline cache `vk_pipelines*.bin`, its prewarm list `vk_pipelines.keys` and the host's temporary saves, so games never share them), `DM_ROOT` in the app's external files folder, `DM_AOC_DIR` (`<files>/aoc/<title ID>`, symbolic links to the DLC folders) in internal app storage (the external folder is shared storage, which refuses symbolic links: [DLC links in shared storage](../docs/reference/packing.md#dlc-links-in-shared-storage-android)), then the lines of `<external files>/env.txt` (`KEY=VALUE`, for diagnostic switches, every game), the game's own lines (Game settings), and `<external files>/env-<title ID>.txt` (the same for one game; later lines win). None of them may set the paths above or `HOME` (refused with a message and a `[RED]` line; the test app takes `DM_SAVE` from `env-<title ID>.txt` for test runs: [TESTING.md](TESTING.md#diagnostic-switches)). A start that fails ends the `:game` process. The host's stdout and stderr go into `<external files>/logs/<title ID>-<time>.log` (the newest 10 of each game are kept), and every line also goes to logcat with tag `nxnative`. Back asks before it ends the game.
- **App storage** (`AppStorage`, as Eden's user folder): `Android/data/<app>/files/` holds the saves (`saves/<title ID>`, `saves/<title ID>_device`) and the packs Prepare makes or Import pack… takes (`packs/<title ID>/`). Each app has its own; Android removes it with the app, and `android:hasFragileUserData` makes uninstalling ask whether to keep it. The host gets plain paths (`DM_SAVE`, the pack folder) as before.
- **A .nup used where it is** (`PickedNup`, `PickedPath`; Add game without All files access › **A .nup file**, or a `.nup` the picker gives no `/storage` path for): the file is picked with the system file picker (`ACTION_OPEN_DOCUMENT`), the read permission kept (`takePersistableUriPermission`: it lasts across restarts until the file is moved or deleted or the permission is taken back), and nothing is copied. The launcher names the game by a stand-in path in app storage, `files/picked/<key>/<its name>` (key: 16 hex digits of the SHA-256 of the document URI; nothing is at that path), which every process (`NxApp`) reads through `Nup.opener`: the provider's descriptor (`ContentResolver.openFileDescriptor`, a regular file read with pread; a cloud provider that only streams is refused, with **Copy into the app** offered). The game's process opens one descriptor and gives the host `fd:<n>/<name>` wherever it would give the path (`DM_ROMFS`, the `DM_AOC_DIR/<index>.nup` links, [NUP.md](NUP.md#a-nup-used-where-it-is)); Prepare's process gives the tools `DM_NUP_FD=<n>:<stand-in path>`; its work folder is `files/picked/<key>/<title ID>-work`, the pack goes to `files/packs/<title ID>` as always. Frontend launches by title ID work as for any card (and a path or URI whose file name is one picked game's, when the app cannot open that path). Remove from list gives the permission back.
- **A game file that is gone** (`GameFile`): a card whose `.nup` or dump folder was deleted, moved or renamed (seen by its path with All files access or in app storage; for a `.nup` used where it is, also a permission taken back) says "Game file gone" and "The game file is gone: <name>. Pick it again, or remove the game." with **Pick it again** (Play asks the same, with Remove). The picked file (a `.nup`, or a folder with All files access) takes the card's place when it holds the same title ID: the card keeps its pack folder, settings and saves (they belong to the title); another game is refused with a sentence. The Readiness check's "Game files" row says the same. A remembered pack folder that is gone (deleted or moved, seen with All files access or in app storage) is not "Needs preparing": the card takes the pack the usual search finds (the app's `packs/<title ID>` first) or, with none, `packs/<title ID>` for Prepare, and a picked pack folder that is gone is forgotten (`Folders.repack`). A picked save folder that is gone is never made again by itself (that would start a new empty save): the card and Play say "The save folder <name> is gone. Use the app's save, or pick the folder again." with both choices, and the game's start refuses it (`GameFile.saveGone`).
- **Copy into the app** (`GameCopy`, `CopyPlan`; Add game without All files access › **A dump folder**): the dump folder is picked with the system picker (`ACTION_OPEN_DOCUMENT_TREE`, the read permission kept with `takePersistableUriPermission`) and copied through the provider into `games/<its name>` in app storage, written as `<name>.part` and renamed when complete; it is then added as a picked game (a `.nup` the provider only streams is copied the same way). The app, the packer and the host read app storage by plain paths, so such a game is added, prepared and played without All files access (`MainActivity.needAccess(game)`, `FrontendLaunch` by title ID), and the Readiness check reports missing All files access as a warning. The cost: the dump takes its size a second time (the copy needs it plus 2 GiB free; the original can be deleted afterwards), and the copy is deleted with the app unless its data is kept on uninstall; Remove from list offers to delete the copy. A folder is not read in place through the picker: the game opens its RomFS files by path, thousands of them, and each would need its own descriptor from the provider; All files access stays the way to read a dump folder where it is. Home's All files access card shows only while a game on the list (or an empty list) would need it.
- **Saves** (`DM_SAVE`): the folder picked in the game's Folders, else the app's `saves/<title ID>`. A save of an earlier version in the old default beside the game (`<Switch2 root>/saves/<title ID>` for the play and release app, `saves-test/<title ID>` for the test app; the root is the folder holding the game folder or the `.nup`) is copied in once at the game's start when the app's save is empty: checked file by file, under both saves' locks, never over an app save, the old folder never changed; when it fails, that start plays the old folder and says so (`SaveMigrate`). An empty save is then filled from the first versions' private save, else from `<Switch2 root>/save-seed/<title ID>`; the log says which (`[nxlaunch] save: <path> (migrated|seeded|existing|new)`, and `copied once from …`). Folders says where the save is. See [TESTING.md](TESTING.md#saves).
- **Packs out and in** (`PackUi`, `PackZip`; a game's ⋯ Manage sheet): **Export pack…** writes the pack as one stored zip, `banana-pack-<title ID>-<version>.zip`, into a picked folder (read back before it gets its name); **Import pack…** takes such a zip or a pack folder of that game, unpacks it beside the app's `packs/<title ID>` (zip-slip names refused), checks it and only then swaps it in, the old pack kept until then ([TESTING.md, Packs in app storage](TESTING.md#packs-in-app-storage)).
- **Save backups** (`SaveUi`, `SaveStore`, `SaveZip`; a game's ⋯ Manage sheet): **Back up saves** copies the game's save folder (the one its next start uses), with its device save `<save>_device` when the game has one, to `<Switch2 root>/save-backups/<title ID>/<yyyyMMdd-HHmmss>/` (shared storage: backups outlive an uninstall) (`main/`, `device/`), checked file by file (path, size, SHA-256) against the save, with a manifest beside it (`<name>.manifest.tsv`); the save is only read. When the app may not write that folder (no All files access) or it is inside app storage (a game copied into the app, a `.nup` used where it is), the backup is made the same way in the app's own `save-backups/<title ID>/` and exported as one `.zip` to a place the user picks (`ACTION_CREATE_DOCUMENT`: `<name>.manifest.tsv` and `<name>/main/…`, `<name>/device/…`), read back and checked against the manifest. Every backup, restore and game start holds the save's lock (`<save>.lock`), which the game keeps while it runs. **Restore saves…** lists the backups the app can see (the shared folder's with All files access, the app's own), with **Import save…** at its end; **Import save…** takes a `.zip` (from Back up saves, or a zipped save folder) or a folder, both through the provider (`ContentResolver` streams, no `/storage` path), unpacked or copied into `files/save-import/` (an entry that would land outside it, zip slip, refuses the whole zip; at most 100,000 files and 4 GiB), and restores from it as from a backup (a backup's manifest is checked; a folder with only `main/` and `device/` is a backup without its manifest). Both back up the current save first (`<time>-before-restore`), then swap the backup in so that the save is the old one or the restored one, never a mix ([TESTING.md, Save backups](TESTING.md#save-backups)). Refused while a game runs. The app never deletes a backup.
- **Game settings** (the game page's **Performance** and **Game** tabs, `GameSettings`; the page is a full page in place of Home: Back returns, a fold or unfold keeps it open, a long name wraps to two lines): a chip with the GPU (GLES's renderer, `GpuGl`) and the driver the game starts with (an installed driver's name, or the system driver from the kept readiness facts, `Readiness.driverWord`: "Adreno 840 · Qualcomm 842.44"), **Recommended** / **Custom** where a recommendation applies ([Recommended settings](#recommended-settings)), then the sections **Picture** (Resolution and its Advanced rows, Upscaler and its sliders, Display, Aspect ratio), **Speed** (Frame rate cap, Hold 60 fps, Full game speed, Dynamic resolution, GPU driver) and **Advanced** (below). The **Game** tab has **Game options** (Full vegetation, the Speedhack "Hidden layers off" with its Experimental tag, the profile's options: each row shows the profile's description, and one whose code patch the pack lacks (`needs=`) adds "Needs Prepare again: patches the game's code"; then Game language) and **Controls** (Rumble, Button mapping, Xbox button labels). **Advanced** is GPU timing, Instanced draws, Classic render passes, Background pipelines, RAM saver, Use fast cores, Pause on return and Extra environment, folded on a phone. A window at least 600 dp wide (an unfolded foldable, a tablet, landscape) shows a rail of the sections at the left and the one picked at the right. A row is a title over its value in up to three lines (for a switch, what its current state does: `Ui.Setting.says`), a status line when it needs something (`Ui.Setting.status`) and its tags on a line of their own; a longer explanation is in the row's picker; a game without a recommendation has **Reset to defaults** at the end. The settings: the game's own resolution, frame rate cap, GPU driver, GPU timing, language and extra environment lines, plus profile-declared opt-in switches (for example The Legend of Zelda: Ocarina of Time's **Max resolution**, **Texture pool ×2** and **Unlocked frame rate**) and, for a profile with `res_preset` rows, one **Resolution** (`ResPresets`, below) whose **Advanced** shows **Window** (Game resolution) and **3D scene** (`SceneRes`: the 3D scene at a fixed scale of the game's own dynamic resolution palette, a RomFS overlay the pack step made from the dump, passed as `DM_ROMFS_OVERLAY`; [Scene resolution from the game's own palette](../docs/reference/frame-rate.md#scene-resolution-from-the-games-own-palette-android)) apart, stored per title ID (`<key>@<title ID>` in the launcher's preferences); each is **Default** until set, which follows Settings (the defaults of every game), or this phone's recommendation where the profile has one ([Recommended settings](#recommended-settings)). The in-game panel's frame rate cap sets the running game's own cap.
- **Game language** (Game settings, `lang@<title ID>`, `GameLanguage`): the language the game is given, as `DM_LANG`: **Phone's language** by default (the phone's locale mapped to the console's code as the host maps `DM_LANG`, so `fr-FR` is French; a language the console does not have sets nothing, so English (US)), or one of the console's 18 languages (SDK 21 added Polish and Thai). A game without that language uses one it has. A `DM_LANG` line in `env.txt` or the game's extra environment wins.
- **GPU timing** (Game settings, `gpu_ts@<title ID>`): what the game's GPU timestamp reports record, passed as `DM_NVN_GPU_TS`: **Game default** (the profile's `gpu_timestamps`, named in the row: per segment for Donkey Kong Bananza, per submission without the key; build.gradle `gpuTsOf`), **Per segment** (each report gets the GPU time of its place in the submission, so a game's dynamic resolution and frame pacing see real GPU time) or **Per submission** (one time for the whole submission, the older behaviour). A `DM_NVN_GPU_TS` line in `env.txt` or the game's own lines wins ([the key](../dm/games/README.md#keys); Donkey Kong Bananza: [Open](../dm/games/040074A01BF12000/README.md#open)).
- **Display** (Game settings, `stretch@<title ID>`): **Fit (keep aspect)**, the default, draws the game's 16:9 picture at the largest size that fits, with black bars on a screen of another shape (4:3, 20:9); **Stretch to screen** fills the whole screen (`DM_VK_STRETCH=1`, `vka_present_fit.h`: one rectangle for the blit, the pre-rotated copy and FSR), so the picture is wider or taller than the game drew it. The on-screen controls and the touchscreen then map to the whole screen (`PictureFit.rect`); a `DM_VK_STRETCH` line in `env.txt` or the game's own lines wins at the start. The in-game panel's **Picture** rows change it while the game runs (below).
- **Button mapping** (`PadMap`, `PadMapUi`; Settings › Button mapping for every game, a game's own in Game settings, `pad_map` / `pad_map@<title ID>`): a row for each Switch button with the controller button that presses it; a tap waits for a press on the controller (a button, an analog trigger past half way, or the hat) and puts it there, swapping with the button it replaces, so each Switch button stays on one controller button. **Save** keeps it for the next start, **Reset to default** drops it (a game's own: back to Settings'). The launcher passes it as `DM_PAD_MAP` (`input_map.c`): a mapped button wins over the A / B swap of Xbox button label swap, which still redraws the prompts; `BUTTON_C` and `BUTTON_Z` can be mapped too. Home (`BUTTON_MODE`) stays the in-game panel's, and the on-screen controls are not changed. The in-game panel's confirm and back are the controller buttons this map makes the Switch's A and B (`PadPanel.confirmBack`).
- **Folders…** (`Folders`, a game's Manage sheet, or Settings › Folders, which asks which game): that game's folder, its pack folder (`pack.tsv` and `shaders/`) and its save folder, each picked with the folder picker and kept per title ID in the app's preferences, so an APK update keeps them. Unset, the defaults above apply. A picked pack folder is used for that title's later game picks; a picked save folder goes to the host as `DM_SAVE` as it is (`[nxlaunch] save: <path> (chosen)`), never migrated into or seeded; when it is empty and the current save folder has a save, the launcher asks before copying (copy never overwrites, nothing is deleted).
- **Storage** (Settings › Storage; `StorageUi`, `StorageScan`): lists what the app wrote that can go, grouped by kind with each item's size and the total, before anything is removed; the player ticks items and confirms a list that names each one. The kinds, found by name under the app's own folders only (external and internal files, cache, no-backup; nothing else there is listed): **old shader library versions** (`packs/<id>/shaders/v-<V>` of an earlier app, only in a pack that already has this version's library: until then the older one is what the game plays), **unfinished copies and imports** (`packs/<id>.partial`, a `packs/<id>.replaced` whose pack is in place, `shaders/.restamp-*`, `games/*.part`, `gpu_drivers/.installing` and a `.replaced-<name>` whose driver is in place, the packer's `pack/*.tmp`), **downloads** (`cache/updates/` but an update waiting for its install, `cache/driver-*.zip`), **RAM saver files** (`cache/dm_fileback_*` a stopped game left), **old logs** (all but the newest of each game, with their digests); not ticked by default: **game temporary files** (`temp/<id>`: the pipeline cache and the game's temporary storage, rebuilt as it plays; never `temp/<id>_cache*`), **packs of games not in the list** and **game copies not in the list**. The pack and the shader library of a listed game go only with its **Remove … data…**, which names the pack folder, its temporary folder, its logs and its DLC links before it removes them (the game stays in the list; a pack outside the app's storage is not touched). **Saves are never listed or removed**: every path is checked against the save folders (`saves/`, `save/`, `save-backups/`, `save-import/`, each game's picked or default save and the older default beside the game) when it is listed and again just before it is deleted, and refused when it is a save, lies inside one, holds one, or sits beside one named after it (`_device`, `.lock`, the restore working folders); links are removed, never followed. Storage refuses while a game, Prepare, a copy into the app, a save backup or a pack export runs. Tests: `python3 dm/tools/tests/test_android_storage.py` (the guard, what is listed and kept, a deletion that leaves every save as it was).
- **Checks before a start**: the pack's code must be of the game build in the folder and of a build this APK supports (`PackCheck.build`, from `pack.tsv`'s `version` and `build` rows and the folder's NSO headers): otherwise the launcher says which builds differ and offers **Prepare again** (a dump) or **Pick pack folder**, instead of a start that would crash. The host loads `<pack>/shaders/v-<DMSH_VK_CHAIN>/dmsh_vk.lib` (`vka_shader.c`); without it the game runs and draws nothing. When it is missing the launcher says which version the pack has and which this APK needs, with **Prepare** (a dump: the shaders only) or **Start anyway**, and **Pick pack folder**.
- **On-screen controls** (`TouchControls`, over the game): a semi-transparent Pro Controller (both sticks, D-pad, A / B / X / Y, L / R / ZL / ZR, − / +, L3 / R3) laid out around the letterboxed picture, multitouch, with a haptic tick on each press. Shown while no gamepad is connected, hidden while one is; the small, faint round button at the top centre (drawn 20 units across, its touch area 48) hides or shows them, and holding it opens the in-game panel; Settings › **Show / hide button** or the panel's controls rows turn that button off (the controls then show whenever the mode says so). The in-game panel has their opacity, size and vibration and the layout editor, and under **Picture** the picture position (kept in the app's preferences). Touches on a control never reach the game's touchscreen; the rest of the picture does.
  - **Layout** (`TouchControls.layout`): sizes are in units of 1/135 inch from the screen's physical dpi (`xdpi` / `ydpi`; the dp instead when the reported dpi is off by more than 0.6–1.6x of the density), which is one dp on the outer screen of the Honor PNM-N49 the layout was tuned on (405 dpi, density 3), so a stick is the same size on every screen and whatever the display size setting. Sticks and D-pad / face buttons anchor to the left and right edges (centred in the side letterbox bars when those are wider than a control), the shoulders and − / + to the top of the control band, the D-pad and right stick to its bottom. The band is the bottom 380 units (2.8 inches, a phone held in landscape) of the view, or all of it on a shorter screen, which also shrinks everything below 340 units high. On the PNM-N49's unfolded inner screen (2352x2172, nearly square, the 16:9 picture letterboxed top and bottom) the controls so stay in the bottom corners in thumb reach, with the D-pad and right stick in the bottom bar, instead of spreading over the 5.4-inch height (the stick and face buttons at 45 % of the height, the shoulders in the top corners). A fold, unfold or rotation while the game runs reaches `GameActivity` as a configuration change (no restart: `configChanges` has `screenSize|smallestScreenSize|screenLayout|density|orientation`), and the view's `onSizeChanged` lays the controls out again with the new display's metrics and hands the host the new layout. The log has `[nxlaunch] on-screen controls: <n> in a <w>x<h> view (<dp> dp high, <px> px a unit, band from y <px>, screen <shape>[, the user's layout]), …` for each layout.
  - **Picture position and the layout editor**: the 16:9 picture is centred by default and can be moved into the black bars, never scaled or cropped (`nxhost_picture_place(x, y)`: 0 left / top, 0.5 centred, 1 right / bottom of the free space; the present, `vka_present.c`, places it from the next frame, generated frames included, and clears the bars wherever they are). On the PNM-N49's inner screen **Top** puts the picture against the top edge and leaves a 2.1-inch black strip below it for the controls. The in-game panel has **Picture › Position (this screen)**: Top / Centre / Bottom, and under On-screen controls **Edit the controls layout…**, which opens the editor over the running game: drag a group (left stick with L3, D-pad, A B X Y, right stick with R3, ZL L −, ZR R +) to move it, put a second finger down to resize it (50–200 %), drag the picture to move it (it snaps to the top, the centre and the bottom); the buttons along the top are Top, Centre, Bottom, Reset and Done. Touches go to nothing else while it is open. Everything is kept per screen shape (the view's size in steps of 40 units: `20x9` is the PNM-N49's outer screen, `20x18` its inner one), so a foldable keeps one layout per screen and a fold or unfold switches between them; a group is kept as an offset in units and a scale around where the automatic layout puts it, so a saved layout follows small size changes and stays inside the view. Prefs `touch_controls`: `group<g>@<shape>` = `dx dy scale`, `picture@<shape>` = `x y`. `TouchControls.positionRows(ctx, box)`, `startEditLayout()` (runs `onEditStart` first, which the in-game panel sets to its close), `picturePosition()` / `setPicturePosition(y)` are what a settings page calls.
- **Graphics self-test** (`SelftestActivity`, in its own process `:selftest`): a full-screen `SurfaceView` whose surface goes to `nxhost_vk_selftest(window, 600)` on a thread of its own, with the on-screen controls drawn over it to try; no game or pack. It shows PASS or FAIL with the return code and logs to `<external files>/logs/selftest-<time>.log` and logcat (tag `nxnative`). Back ends its process.
- **GPU driver download** (`DriverFetch`): **GPU driver…** → **Install…** → **Download…** lists the `.zip` assets of the public GitHub releases of six Turnip / Adreno driver repositories (the list is `DriverFetch.REPOS`); a tap on one downloads it into the cache, installs it like a picked zip (it needs a `meta.json`) and picks it. Nothing is downloaded without a tap, and no driver is in the APK ([NOTICE.md](NOTICE.md)). This is the only use of the `INTERNET` permission.
- **adb**: `am start -n dev.nxnative.android/.MainActivity --es game <game folder> [--es pack <pack folder>] [--ez run true]` adds a game without the pickers and starts it; `--es add_game <folder or .nup>` takes Add game's own path for what the picker would return (a folder's games all added, the summary, Prepare asked).

- **Overlay** (`GameActivity`, `Overlay`, on by default): top left a small build tag, top right the frame rate and what the phone is doing, bottom left the log's last lines while it shows (until the first frame, after a crash, or with Show log on): all at one size, 8 sp, white on a faint dark pill with tight padding, flush in their corners and clear of the touch buttons there; the log block grows at most up to the tag's bottom edge. The build tag is `Banana Native 0.1 · <commit>` in the play app and `Banana Native test · <branch without "android-">@<commit>` in the test app (no build time: the commit and the signer's fingerprint identify a build) (`+dirty` after the commit when the tree had changes; Gradle reads git at build time, `unknown` without it); the same line is in Settings › About and is the first line of every game log, `[nxlaunch] build …`; Home shows only its build identifier under the title (`launcher-2@4a15067`, `0.1 · <commit>`: `Signer.buildId`, which the tag is made from, so the two never disagree). Top right, one short item a line so that the block fits in the black bar beside the game's 16:9 picture on a wide phone (off the game's HUD): a **throttle dot** and the game's frames a second (with frame generation on `<game>→<presented> fps` and `LSFG`), the frame time, the GPU's busy time a frame (`GPU <ms>`, the submissions' timestamps averaged over the last 32 frames whose time is in), the CPU clock caps (`CPU 2.5/3.6` then `1.9/4.6 GHz`: each cpufreq cluster's `scaling_max_freq` / `cpuinfo_max_freq`, main cluster first) the battery (`41°C 87%`, `⚡` while plugged in) and the memory: `App 4.3 GiB`, the game process's resident set (VmRSS in `/proc/self/status`, shared pages counted whole; not PSS, which `Debug.getPss` walks every mapping for), then `RAM 9.8/14.7 GiB`, the phone's in use / total (ActivityManager.MemoryInfo `totalMem - availMem` / `totalMem`, GiB as the readiness check's `ram_gib`), with a red `low` while Android's `lowMemory` is set (`MemText`; read on a thread of its own, `overlay-mem`). The dot is red for thermal status MODERATE or worse (`PowerManager.getCurrentThermalStatus()` ≥ 2), thermal headroom ≥ 1.0 (`getThermalHeadroom(10)`, SEVERE) or the main cluster (the policy with the most cores) capped below 65 % of its top clock; yellow for status LIGHT, headroom ≥ 0.85 (the PNM-N49 reads 0.69-0.75 at full clocks) or a cap below 85 %; green otherwise (grey: nothing readable). On the PNM-N49 the game holds 30 fps with cpu0-5 at 2.5 GHz of 3.63 (69 %, yellow, the cap the phone keeps even when cool) and drops to 20 fps at the 2.0-2.23 GHz caps (55-61 %, red) it sets once warm, while the thermal status still reads 1. The log gets `[overlay] throttle <colour>: …` with the readings when the colour changes (at most every 10 s). Read twice a second (`nxhost_fps` from `vka_fps.c`; headroom, battery and memory every 2 s), nothing while the overlay is off. The launcher draws the build tag and the top-right block into bitmaps when their text changes (`Overlay.Block`, a styled `TextView` never attached) and hands them to the host, whose present draws them into the game's own images in their corners (`vka_present.c` `ovl_draw`, every preTransform, generated frames too), so the app's window over the `SurfaceView` stays still: as views that changed twice a second they made the window render on the GPU and the compositor blend a second changing layer, which cost a GPU-bound game frames ([issue #34](../docs/reference/frame-rate.md#the-overlay-as-android-views-over-the-games-surfaceview)). The views show them only while the present has not drawn them yet or does not (`DM_VK_OVERLAY=0`, live, or a failure), and their text is set only when it changed. Settings: a master switch and one switch per item (build tag, frame rate, throttle dot, GPU time, CPU caps, battery, memory), all on by default (main screen: the checkbox and **Overlay items…**; in the game: the in-game panel); `DM_OVERLAY=0` / `1` in `env.txt` overrides the master switch for a run. The log also gets `[vk] fps: …` every 15 s.
- **Official-build stamp** (`Signer`, `Prefs.signers`): the play and release apps end the build tag with `· official` when the APK's own signing certificate (PackageManager `GET_SIGNING_CERTIFICATES`, its current signers) has the release key's SHA-256 (`Signer.OFFICIAL`, from the v0.1.0 release APK) and is the only signer, else `· unofficial build`; the test app makes no claim. The first game-log line (`[nxlaunch] build … · signer <16 hex>`) and the readiness report (`Signer:`) carry the first 16 hex digits of the signer's SHA-256, so a bug report shows which key signed it. It is a convenience, not a proof: a modified app can print any text; what a user verifies is the certificate (`apksigner verify --print-certs <apk>`). Tested on the JVM by `dm/tools/tests/test_android_signer.py`.
- **Controllers and players** (`PadOrder`, `GameActivity`): each gamepad is a player of its own. An external controller (USB or Bluetooth, `InputDevice.isExternal`) gets its player when it connects, a controller with gamepad buttons and a stick first, and takes player 1 from any device that is not one; a device built into the phone gets a player only from its first input (a button, or a stick or trigger past half), so a system device that looks like a gamepad (Xiaomi's "uinput-xiaomi") takes no player while it is silent and does not hide the on-screen controls. The in-game panel's **Controllers › Player 1** shows the device on player 1 and picks another (or **Automatic**); the choice applies at once (`nxhost_input_device_first`: the two devices trade players) and is kept for every game (`pad_first`, the device's descriptor).
- **Game resolution** (`MainActivity`, `Prefs.window`; Settings › **Resolution**, or a game's own in Game settings): the window size the host gives the game, from the next start: **Phone 1080p** (the default, `DM_WINDOW_SIZE=1920x1080`; a profile's `android_window` can give its game another default when the player has chosen none, on this screen or in the game's own settings: Fire Emblem Fortune's Weave names Phone 1080p, the default itself; Donkey Kong Bananza's Phone 720p of v0.1.2 went with its upscaler fix and Turnip's GPU clock floor), **Original** (`DM_WINDOW_SIZE=original`, the game's own size: 2880x1620 in Donkey Kong Bananza), **Phone 1440p** (`DM_WINDOW_SIZE=2560x1440`: for QHD screens, which would otherwise stretch 1080p), **Phone 540p** (`DM_WINDOW_SIZE=960x540`: for the weakest GPUs), **Phone 480p** (`DM_WINDOW_SIZE=848x480`: for the lowest GPU load) or **Phone 720p** (`DM_WINDOW_SIZE=1280x720`: less GPU time a frame on a GPU-limited phone; it saves only tens of MB of memory, the game's own memory does not depend on it). The setting stores the size itself, so the list's order can change (it is listed from the largest). The host writes it into the game's window-size functions at load (profile key `window_fn`, `loader.c` `window_apply`; the log line `window: …`); the render targets scale with the window. A game with dynamic resolution and a `res_levels` row instead (Pokémon Pokopia) takes the same `DM_WINDOW_SIZE` as a cap on its render size: the host lowers the level lists that start above it (`loader.c` `levels_apply`; the log line `resolution: at most …`), and the game keeps its own maximum and draws into part of its render targets ([the game note, Render size](../dm/games/0400A3A01EE4C000/README.md#render-size)). A game with neither row for its build keeps its own size. A game that sizes its scenes by the Switch 2 graphics scale instead of its window has `graphics_scale` rows in its profile ([the key](../dm/games/README.md#keys)): the same choice then sets `DM_GRAPHICS_SCALE` and `DM_OPMODE` from the choice's row and no `DM_WINDOW_SIZE` (Mario Kart World: 1080p = handheld scale 0, 1920x1080; 720p = handheld scale 2, 1280x720; Original = its own, console scale 1, 2048x1152; [Render resolution](../dm/games/0400C3F00006E000/README.md#render-resolution-android-180))). Such a game has only the sizes its scales give, so a size without a row of its own takes the row of the largest size that fits in it, or the smallest row when none fits: every choice does something (Mario Kart World, Splatoon Raiders and Ocarina of Time: 1440p = console scale 1, 540p and 480p = 720p's row). A game whose rows are one console row and one handheld row only gets two choices instead, as radio buttons in Game settings and the in-game panel: **Docked (<height>p)** and **Handheld (<height>p)**, each its own row (`Profile.modes`; Fire Emblem Fortune's Weave: Docked (1152p), 1024x576 to 2048x1152, and Handheld (1080p), 960x540 to 1920x1080, the default). The in-game panel has the same choices under **Resolution** for a game with a lever, and a choice there is the game's own setting: a game with `graphics_scale` rows changes at once (the host takes the row's scale and operation mode and posts the console's notifications 300 and 30 / 31, which the game answers by querying them again: `Native.graphicsModeSet`, [Graphics scale changes while the game runs](../docs/reference/services.md#graphics-scale-changes-while-the-game-runs-message-300)); a `window_fn` or `res_levels` game takes it at the next start. Which lever a game has comes from its profile (`Profile.resolutionEnv`, build.gradle `resolutionOf`); a game with neither gets no Game resolution row in its Game settings, and Settings shows the default only when a game of the APK has one. `env.txt` lines still win for a run. `DM_WINDOW_SIZE=<w>x<h>` in `env.txt` overrides the setting for a run. The pack carries the game's own constants: a Donkey Kong Bananza pack made before this setting has them cut to 1920x1080, which the host overwrites either way; to replace it, run the packer again (above) and copy the new `main.*` files over the phone's pack folder ([the game note, Window size](../dm/games/040074A01BF12000/README.md#window-size)).
- **Resolution presets** (`ResPresets`, `Prefs.resolutionChoice`; a game whose profile has `res_preset` rows, [the key](../dm/games/README.md#keys)): Game settings › **Resolution** offers the profile's presets, each setting the window (its `graphics_scale` row) and the 3D scene inside it (the game's own palette, or the preset's overlay, `scene_res/<id>`) together, with a second line that says what the player gets ("window 1280x720 · 3D about 960x540"; "about" until the profile marks the window's output measured), and **Advanced (for testers)**, which shows Window and 3D scene apart as before. The default is the profile's first row (Ocarina of Time: **Quality**, 1080p with the game's own dynamic resolution, its start before the presets; then **Balanced**, **Performance**, **Max performance**). A player who chose neither a preset nor Advanced gets the preset their older Game resolution (the game's own or Settings') and Scene resolution match, else Advanced with those choices as they were (`ResPresets.current`), so nothing changes for them until they pick. The start logs `[nxlaunch] resolution <id or advanced>: window …, scene …` and, for an overlay, the `scene resolution` line (red with Prepare again when the pack has none). The in-game panel's Display › Resolution offers the same presets: the window changes at once, the 3D scene at the next start (the overlay is read when the game loads). Reset to defaults forgets the choice. Tested by `test_android_res_presets.py` (`ResPresetsJvmTest`) and `test_scene_res.py`.
- **In-game panel** (`SidePanel`, over the running game, which goes on behind it): opened by a swipe in from the right edge (an invisible strip there, from a sixth to half way down; under gesture navigation the system's Back swipe from that edge does the same), the phone's Back, holding the on-screen controls' top-centre button, or a controller (below); closed the same ways, by a tap beside it, by its ✕, or by the controller's B. A hint at the right edge says how, once per install (`panel_hint`). Its rows are in four tabs under a tab bar, so that each fits a phone held in landscape (1080 × 2420) with little scrolling:
  - **Performance**: the frame rate cap (and Full game speed at low frame rates), the Upscaler (for games whose neural upscaler it replaces), the dynamic resolution and frame generation; their live lines refresh twice a second while this tab shows.
  - **Display**: **Resolution** (Game resolution, or the Resolution presets for a game with them; the window live on games with `graphics_scale` rows, else from the next start), the picture (below) and the overlay's items.
  - **Controls**: **Controllers › Player 1** (shown while a gamepad is connected), the on-screen controls (Auto / On / Off, opacity, size, vibration, the log, the show / hide button and the layout editor), **Rumble** (the game's vibration on the controller or the phone: the game's Game settings › Rumble, applied at once: off mutes it, on starts it even when the game started with it off; `GameActivity.rumble`, `Rumble.mute`) and the **Button mapping** shortcut for the next start.
  - **General**: the panel's own look, **Pause the game**, Pause on return, **Stop the game** and **Back to the game**.

  Each change applies at once and is kept for the next start, except the shortcut. The tabs are 48 dp high at least (the panel's row height), the selected one filled yellow with dark text, each named for TalkBack ("Display tab, 2 of 4, selected").
  - **With a controller** (`PadPanel`, `SidePanel.padKey` / `padMotion`, `GameActivity.dispatchKeyEvent`): Settings › **Controller: in-game panel** picks how a controller opens and closes it: **Home, or hold − and + (half a second)** (the default: Home / guide, `KEYCODE_BUTTON_MODE`, which the host never takes, or Select and Start held together, as other emulators do), Home only, − and + only, or Off. − and + still reach the game while they are held (a game that reads + alone sees it); when the hold fires the panel opens and their releases are eaten. When the panel opens, every pad button the game holds is released and every stick centred (`releaseGameInput`), so nothing stays pressed; while it is open no pad key or axis reaches the game, and a key the panel took a press of stays the panel's until it comes up. In the panel: the D-pad, its hat or the left stick move the focus row by row (held: again after 0.4 s, then every 90 ms), left / right step a slider or a radio group (in a list from the checked choice), A presses, B closes, L / R switch tabs, and the focused row has a yellow frame. A and B are the buttons that are the Switch's A and B in this game (its Button mapping, or Xbox button label swap's "swap buttons A/B"): by position A is the right button and B the bottom one, as in the game. The panel's own dialogs (Stop the game?, Player 1) take the same buttons and open with the focus on their safe choice; the Button mapping editor keeps Android's (bottom confirms). The panel opens the same with the on-screen controls shown or hidden and with frame generation on.
  - **Picture** (per game, `stretch@<title ID>`, `picture_size@<title ID>`): **Fit** / **Stretch** (the same setting as Game settings › Display) and **Size** 50–100 % in 5 % steps (`DM_VK_PICTURE_SIZE`: the fitted or stretched picture shrunk with its shape kept, black around it), then **Position (this screen)** Top / Centre / Bottom. A change reaches the running game as `env DM_VK_STRETCH=…` / `env DM_VK_PICTURE_SIZE=…` lines of its live control file (`DM_CTL`, [TESTING.md](TESTING.md#live-control)), which the present applies at its next frame (`vka_present.c`, `vka_present_fit.h`), and the on-screen controls and the touchscreen are mapped to the same rectangle at once (`PictureFit.rect`, the launcher's twin of `vka_fit_rect`: `dm/tools/tests/test_android_panel.py` runs both over a grid). The next start passes them as environment lines (a `DM_VK_STRETCH` or `DM_VK_PICTURE_SIZE` line of `env.txt` or the game's own lines wins there). With `DM_CTL=` (no live control) the rows say the change applies at the next start.
  - **Panel** (every game, `panel_size`, `panel_text`): **Size** Small / Normal / Large (the panel's width, 340 / 420 / 520 dp at most 45 / 55 / 70 % of the screen's width, and the least height of each row: 40 / 48 / 60 dp) and **Text size** Small / Normal / Large (every line × 0.85 / 1 / 1.2): `PanelLook`. The panel is built again at once in the new look, the focus left on the choice.
  - **Next start**: **Button mapping** (this game's own, `PadMapUi.forGame`) and **Game language** (`GameSettings.language`), the dialogs of Game settings; each row says it applies at the next start, since the host reads `DM_PAD_MAP` and `DM_LANG` only when it starts.
  - With a gamepad every row is reached with the D-pad (up / down between rows, left / right between choices and along a slider: 5 % a press for Size, Opacity and the controls' Size), A presses or picks, B closes.
- **Pause** (in-game panel **Pause the game**, and on return): the game is suspended while its screen shows, with "Paused, tap to continue" over it; a tap, or A / Start on a gamepad, continues. With **Pause on return** on (per game, on by default: its Game settings, or the in-game panel's checkbox) the screen coming back from the background shows it paused instead of letting it run at once. Suspended (paused, or in the background) means: the guest clock frozen, the graphics drained and gated, every guest thread stopped at its next SVC, spin gate or sleep (`dm_guest_suspend`, `hle_os.c`: Horizon suspends the whole process, and guest sleeps and timed waits run on host time, so a frozen clock alone left them waking), audio suspended (the silent sink idle), the motion sensors off, the launcher's overlay and log tail idle, the watchdog counting no stall (a game that has not committed its save keeps that progress only in memory meanwhile, frozen as Horizon's suspend freezes it: stopping the game while paused or in the background loses it); the game is told Background (focus 3 after 2), and OutOfFocus then InFocus when it continues (`nxhost_lifecycle` events 4 / 5). Each change logs `[lifecycle] paused | continued | background | foreground: threads' CPU since the last pause or resume <s> in <s> (<n> threads); busiest: …` from `/proc/self/task`, so a background or a pause shows what still ran.
- **Frame rate cap** (in-game panel, `DM_FPS_TARGET`; kept as the running game's own cap, `fps_cap@<title ID>`; Settings' is the default of the others): the game's own, 60, 30, 20 or 15 fps, set while the game runs (`nxhost_fps_cap_set`, `hle_fpslock.c` `dm_fps_target_set`). The host writes it into the game's own frame-rate limiter, so the game runs at that rate and at the right speed; a rate the game's limiter cannot hold is greyed. 40 and 45 are not offered: a game that steps its logic by its present interval runs at the wrong speed at them ([A dynamic interval controller's floor, and caps set while the game runs](../docs/reference/frame-rate.md#a-dynamic-interval-controllers-floor-and-caps-set-while-the-game-runs)); a stored 40 or 45 reads as 30 (`Prefs.capOf`). A game that picks its own frame rate (the host's cap status reports no rate it can hold) gets no cap choices: the in-game panel shows one line instead, and once a run has seen it (`own_rate@<title ID>`, written 30 s after the start and by the panel) its Game settings show the cap as "This game picks its own frame rate". The cap is the game's own rate; frame generation (below) is a separate setting that adds generated frames on top.
- **Full game speed at low frame rates** (Game settings, under the frame rate cap, and the in-game panel, next to the frame limit; per game, `decouple@<title ID>`, on by default; only for a game whose profile has `fps_decouple sead`): the game keeps its normal speed when its frame rate drops or is limited, because the host hands sead's frame-rate controller the measured rate ([the entry](../docs/reference/frame-rate.md#a-game-whose-speed-follows-its-present-interval-runs-slow-when-frames-come-late)). Off, the game slows down with its frame rate, as on the console. The panel changes it while the game runs (`Native.decoupleSet` → `nxhost_fps_decouple_set`, read at the next frame); a start with it off passes `DM_FPS_DECOUPLE=0`, which an `env.txt` line overrides.
- **Settings are kept** across game and app restarts: the launcher (main process) and the game (`:game`) share the preference files, read again whenever the other process wrote them (`Prefs.open`, `MODE_MULTI_PROCESS`), and every change is written at once (`commit`), so stopping the game, which ends its process, loses nothing.
- **Frame generation (LSFG)**, off by default: Lossless Scaling's frame generation, with the user's own `Lossless.dll` (Lossless Scaling for Windows). The launcher looks for it, in order, at `Documents/Emulation/bios/Lossless.dll`, `Switch2/Lossless.dll`, `Download/Lossless.dll` and `Android/data/<app>/files/Lossless.dll` on the phone's storage, and copies the first it finds into the app's private files (again when it changes); Settings › **Frame generation** shows what it found and has **Pick Lossless.dll** for a file elsewhere. Settings (Settings › Frame generation, or in the game: the in-game panel): on / off, frames per game frame (2x, 3x, 4x), a target frame rate instead (60, 90, 120: the multiplier follows it, Eden's pacer), and the motion estimation resolution (Auto = the game's own resolution, 25–100 %). Changes in the game apply from the next frame. The host gets them as `DM_LSFG=0/1`, `DM_LSFG_MULT`, `DM_LSFG_TARGET`, `DM_LSFG_FLOW` (0 = auto) and `DM_LSFG_DLL` (the copy), which `env.txt` can override. Generated frames are presented between the game's frames, each held for its share of the game's measured frame interval (display timing); the game's own frame is shown last, so the picture is one game frame behind. Needs `shaderFloat16`, storage images of R8 / RGBA8 / RGBA16F and null descriptors; without them, or without a usable DLL, the overlay says `LSFG unavailable` and the log has `[RED] vk: frame generation unavailable: <why>`. Only Eden's performance shader set is used.
- **Upscaler** (Game settings › Upscaler, Settings for the default of every game, and the in-game panel; per game, `ndsr_choice2@<title ID>`, `ndsr_sharp@<title ID>`; `GameUpscaler`): what runs in place of a game's own neural upscaler (agl's NDSR network, emulated and slow on phones: `DM_VK_NDSR`, `dm/gfx/vk_android/vka_draw.c`) and how a picture smaller than the screen is scaled to it: Nearest neighbor, Bilinear, FSR 1 (with **FSR sharpness** Off, Softer, Soft, Default, Max: `DM_VK_NDSR_SHARP`, and FSR at the present, `DM_VK_FSR`, `DM_VK_FSR_SHARP`), Native (the game's network itself) or SGSR 1 (the default). The in-game panel's **Upscaler** rows are the same per-game setting as Game settings (a change in one shows in the other) and apply from the next frame: the panel sends `env DM_VK_NDSR=…`, `DM_VK_NDSR_SHARP`, `DM_VK_FSR`, `DM_VK_FSR_SHARP` and `DM_VK_PRESENT_NEAREST` lines to the running game's live control file (`DM_CTL`, [TESTING.md](TESTING.md#live-control)); the host takes the new choice at the network's next dispatch, in every direction, Native included (the network's own pipeline is made at its first dispatch whatever the choice) and logs `NDSR upscaler: DM_VK_NDSR=<n> (<name>) from network <key>'s next dispatch on (a live change)`. The rows show only for a game whose network the host can replace: the host says so once the network has run (`nxhost_ndsr_status`, `Native.ndsrStatus`; so far Donkey Kong Bananza (`040074A01BF12000`) and Ocarina of Time (`0400486024DEC000`)), and the launcher remembers it per game (`ndsr_seen@<title ID>`), so from the next start they are there before the network's first frame. A game whose network does not fit (another input or output format: it always runs) or that has none gets no rows; its Upscaler choice still sets the present's scaling, from Game settings. The FSR sharpness row shows while FSR 1 is the choice. With `DM_CTL=` (no live control) the rows say the change applies at the next start; an `env.txt` or `env-<title ID>.txt` line wins at the start.
- **Notice for skipped work** (`GameActivity`, `SkipNotice`; `DM_VK_SKIP_WARN`, default 5 %, 0 = off): when the Vulkan replay skips more than that share of a game's draws and dispatches for causes of the GPU or its driver (refused pipelines and shaders, a mesh draw without `VK_EXT_mesh_shader`, a feature the device lacks; not the game's own skips) in two windows of 300 frames in a row, never in the first 900 frames, the host logs one `[RED] vk: <n> % of draws skipped over the last 300 frames (causes: ...)` line and answers `nxhost_skip_status`. The game screen asks every 5 s from 30 s after the start (`Native.skipStatus`) and shows once per run a small notice at the bottom: "Part of the picture is not drawn on this GPU driver (<n> % of draws skipped). Another driver may draw it: Settings › GPU driver, or this game's Game settings. Driver now: <System or the driver's label>." When the largest cause is a device without mesh shading (no `VK_EXT_mesh_shader`, e.g. Adreno 7xx on either driver), the text says only that this GPU has no mesh shading so some models are missing (no driver advice). A tap dismisses it; it fades after 20 s. See [rendering.md](../docs/reference/rendering.md#skipped-work-warning).

### Recommended settings

A game's profile can recommend settings per phone (`game.tsv` `recommend` rows: [the key](../dm/games/README.md#recommended-settings); `Recommend.java`, `Prefs.recommended`): Resolution preset, GPU driver, Upscaler, Hold 60 fps, Frame rate cap, Dynamic resolution, Full vegetation, the Speedhack and the profile's options.

- **Matching:** a row matches on what the GPU driver reports (the [readiness check](#readiness-check)'s facts: `driver.id`, `driver.version`, `gpu.vendor`, `gpu.device`, features, extensions, limits), never on a name. The launcher keeps the facts of each driver it has checked (`vk_facts@<driver>` in its preferences, written by the start-up check and the Readiness check screen); a driver row matches the system driver's facts, the other rows the facts of the driver the game starts with. Until a check has run on the phone's own driver, the launcher keeps stand-in facts for it from GLES at its start (`GpuGl`, `Recommend.glFacts`: the vendor from `GL_VENDOR`; on Qualcomm's own driver, whose `GL_VERSION` carries `V@<minor>.<patch>` as its Vulkan `driverVersion` does, `driver.id` 8 and that version), so the recommendations show from a fresh install on; the first check's own answer replaces them. A start whose `DM_VK_DRIVER` line says `system` keeps its facts as the system driver's (`Recommend.probedChoice`). Without either, only `any` rows apply. A recommended GPU driver must be installed and known (from a check) to report the driver ID the row names; otherwise the row is left out. The game's process keeps the recommended driver it checked for the whole start (`Prefs.pinDriver`): the driver opens once a process.
- **Order:** the game's own value (Game settings, the in-game panel) wins, then the recommendation, then the main screen's default (Settings), then the built-in default. Nothing is written: a release that changes a row reaches everyone who did not set that setting for the game.
- **Game settings:** when a recommendation applies, a card on top, **Recommended for this phone**, has **Recommended** / **Custom** over the recommended values by short name ("Performance · Turnip V39 · Hold 60 off"). It shows Custom when the player changed some of them, with a muted line "You changed N of these. Recommended puts them back."; picking **Recommended** (after a confirm, **Use recommended**) removes the game's own values of those settings and keeps the others, and **Custom** keeps the player's values (it changes nothing). The card takes the place of Reset to defaults; a game without a recommendation keeps Reset. Each row of a recommended setting has a tag on its second line, before its value, **Recommended** (accent tint) or **Changed** (warning tint, with a muted "Recommended: <short name>" line under the value); toggles update the tags and the card at once (`GameSettings.decorate`, `Ui.tag`). Rows show their value alone (no "Default · " prefix); a list's first choice says "Recommended (…)" or "Default (Settings: …)".
- **Log:** every start writes one line, `[nxlaunch] settings: Resolution performance (recommended), GPU driver system (default), Upscaler sgsr1 (yours), …`: each of these settings the game offers, its value in the row's words, and its source (yours, recommended, default). `env.txt` and the game's own environment lines come later and win, as for every setting.
- **Tests:** `python3 dm/tools/tests/test_android_recommend.py` (the JVM test `RecommendJvmTest`: matching, later rows winning, driver resolution, the value order; the value lists of `build.gradle`, `dm/tools/recommend.py` and `Recommend.java`; every profile's rows).

## Readiness check

What a phone must have for a game, checked before the game starts and on its own screen (Settings › **Readiness check**), so that a player on a phone that lacks something gets a sentence naming it instead of a crash or a broken picture.

**Tested:** one phone, an Honor PNM-N49 (Adreno 840, 16 GB, Android 17) on its own Qualcomm driver (driver ID 8, `QUALCOMM_PROPRIETARY`), and the Turnip builds in [Custom GPU drivers](#custom-gpu-drivers). Every other phone, GPU and driver is untested: the requirements below are what the code and the shader libraries need, not a list of phones that work.

| Class | What | Missing means |
|---|---|---|
| Every game: the phone | 64-bit ARM, Android 13 (SDK 33) or newer, All files access for a dump folder read where it is (a `.nup` picked with the file picker, or a folder copied into the app, needs none) | the app does not install, or cannot read the game |
| Every game: Vulkan | Vulkan 1.3 (loader and driver), one graphics + compute queue, timeline semaphores, dynamic rendering (`vka_dev.c` stops without them); `VK_KHR_swapchain`, `VK_KHR_map_memory2` + `VK_EXT_map_memory_placed` (`memoryMapPlaced`), update-after-bind sampled image arrays (partially bound, runtime arrays) | the host stops, or runs and draws or shows nothing |
| Per game: memory | at least the game's `ram_gib` (ActivityManager `totalMem`, which on a 16 GB phone is about 14.5-15.5 GiB) | required: Android stops the game; degraded: tested on more only |
| Per game: shader features | the features the game's shader library uses (geometry shaders, storage images without a format, draw parameters, buffer device addresses, 64-bit integers ...), and `maxComputeSharedMemorySize` at least its largest compute shader's | required: those draws are skipped or the pipelines fail; degraded: a few shaders |
| Per game: textures | `textureCompressionBC` and `textureCompressionASTC_LDR` (textures are sampled in their own formats, never decoded on the CPU) | that texture is missing |
| Per game: sparse textures | sparse residency images (binding, 2D residency, the standard block shape, strict non-resident reads, on the queue) and sparse residency per format (BC6H, ASTC 8x8 ...) | degraded: a texture array is a dense image starting at a coarser level (less detail, more memory). A format with sparse residency takes only the tiles the game maps (`vka_sparse.c`); one without gets a dense image from the finest level that fits `DM_VK_SPARSE_DENSE_MB` (`vka_tex.c` `dense_floor`) |

Each game's own rows are in its profile, `dm/games/<title ID>/readiness.tsv` ([the format](../dm/games/README.md#readiness-rows)), with a status row (`playable` or `bring-up`: a game in bring-up gets a warning on every phone). The host's own needs are `Readiness.HOST` (they mirror `vka_dev.c`).

- **The facts** (`nxhost_vk_readiness`, `dm/gfx/vk_android/vka_readiness.c`): an instance of its own on the driver the game would load (the launcher's pick or a `DM_VK_DRIVER` line, opened once per process, so the replay gets the same library), the first physical device (the one the replay takes), no device: the API version, the GPU's name, vendor and device IDs, the driver's name, info, ID (`VkDriverId`) and version, a custom driver's name, the features and limits above, the extensions, the queue, the sparse properties, per format whether a sparse residency 2D array can be made (as `vka_tex.c` asks), and the device-local heap. Nothing knows a vendor: a custom driver is checked by what it reports. The launcher adds `ram_gib` and `android.sdk`.
- **Before a start** (`GameActivity.readinessHold`, after the pack and RomFS checks, before the save is locked and `nxhost_main` starts; at most 8 s: a check that does not answer, or a host that cannot report, gives one "not checked" warning, never a failure): required items missing → **Not ready for this game**: the missing items by name, and **Back**, **Details** or **Try anyway**; when placed memory maps are missing (`VK_KHR_map_memory2`, `VK_EXT_map_memory_placed`, `memoryMapPlaced`) it says plainly that with this driver nothing is drawn (a black screen), suggests System (or, on System, a custom driver that has them), and the button reads **Start anyway (black screen)**; **Details** has each item with what the driver reports and what the game needs, the GPU and driver, and **Copy report**. Degraded items only (or a game in bring-up): the game starts with no notice (since 2026-11-11; a **Ready, with limits** notice with **Continue** stopped every start before); Settings › Readiness check shows them. The log gets one line, `[readiness] <title ID>: PASS|WARN|FAIL; <GPU and driver>; RAM …; missing (required): …; missing (degraded): …` (and "the player chose Try anyway"), and `files/readiness-<title ID>.txt` the full report of that start.
- **The screen** (`ReadinessActivity`, in its own process `:readiness`, which loads the first game's host to ask the GPU): a verdict (Ready, Ready with limits, Not ready) with **Run again**, **Share** (a long press copies) and **Copy report**, then pass / warning / fail rows for the phone (Android and ABI, memory, All files access, free storage, battery restrictions, the last game exit and the memory kills of the last 7 days from Android's exit records, the test app's `env.txt` switches), the GPU and driver, and each game of the APK (named as the user's added game, else by title ID); a row's details open on a tap (failures and warnings, and the GPU's facts, open from the start, with a fix button where there is one: **Allow file access**, **Open the app's settings**, **Pick a GPU driver**). The report is the whole check as text, with each game's last start-up check and every fact, for a compatibility report. A game with a driver of its own is checked on that driver when it starts: its row **Its own GPU driver** is a warning when that driver differs from the one the screen checked (the driver opens once a process, so the screen cannot probe a second one).
- **The tested phone** (2026-11-03, its own driver; the facts are `android/app/src/jvmtest/honor-pnm-n49.readiness.txt`): Adreno (TM) 840, Vulkan 1.4.295, Qualcomm 718a07726a (driver ID 8, version `0x8034a02c`), 14.7 GiB; every host need present. Of the two games one passes every check, the other (in bring-up) warns: `maxComputeSharedMemorySize` is 32,768 where 168 of its compute shaders take 49,152, and no block-compressed format has sparse residency (RGBA8 and RGBA16F have), so its BC6H and ASTC 8x8 arrays start at a coarser level. It also reports `VK_EXT_mesh_shader` with `meshShader` and `taskShader` (mesh / task shared memory 32,768), no `shaderFloat64`, subgroups of 64.
- **The environment of the check:** the game's, as `start` sets it (the launcher's settings, then `env.txt`, the game's settings, `env-<id>.txt`; not the paths), so a driver that reads a variable only at its first device (Mesa's `FD_DEV_FEATURES`, `TU_DEBUG`) sees it: the check makes that device in the game's process ([the entry](../docs/reference/rendering.md#a-driver-variable-in-the-games-settings-has-no-effect-on-the-vulkan-replay)). A user line whose `DM_` name no part of the build reads gets a `[RED]` line in the game's log, with the nearest switch's name, and a toast.
- **Tests:** `dm/tools/tests/test_android_readiness.py` (the decisions on the JVM; every profile's rows name a fact the host or the launcher reports).

## Custom GPU drivers

The replay runs on the phone's own Vulkan driver (**System**) unless another is picked. A custom driver is a zip in the layout Eden and other Android emulators use: the driver `.so`, anything it loads, and a `meta.json` whose `libraryName` names the `.so`.

- **Install and pick:** Settings › **GPU driver** → **Install…** → **Pick a zip…** (the system file picker), **Download…** (the public GitHub releases of the repositories in `DriverFetch.REPOS`; only on a tap), or a zip put in the app's own `Android/data/<app>/files/gpu_drivers/` (listed by name). The launcher never opens files in other folders (Download, …) by itself. The zip is unpacked off the UI thread into the app's private files, `files/gpu_drivers/<name>/`, the only place a library may be loaded from, and the picked one goes to the host as `DM_VK_DRIVER=<that folder>` when the game starts. **System** passes nothing. adb: `am start -n dev.nxnative.android/.MainActivity --es gpu_driver_zip <zip path>` installs and picks a zip, `--es gpu_driver system` goes back.
- **A failed install** (`DriverZip`) is a message, never a crash: a damaged zip, an entry name that is not UTF-8 (Java's zip reader throws `IllegalArgumentException` for it), no `meta.json`, a missing library, more than 256 files or 512 MB unpacked. It is unpacked into `gpu_drivers/.installing` first and replaces an installed driver of the same name only once checked, so a failure leaves the installed drivers and the pick as they were. Tests: `python3 dm/tools/tests/test_android_driverzip.py`.
- **Host:** `DM_VK_DRIVER=<folder>` (or a `.so`) loads that driver through libadrenotools (`vka_driver.c`; `dm/third_party/libadrenotools`); a `DM_VK_DRIVER` line in `env.txt` wins over the launcher's pick. `DM_VK_HOOKDIR` overrides where the hook libraries are (by default beside `libnxhost.so` in the APK). Both restart only. The log's `[vk] driver: <name> (<info>), driver ID <n>` line says which ran; each driver keeps its own pipeline cache file.
- **Per-driver defaults** key on `VkPhysicalDeviceDriverProperties.driverID` (`V.driver_id`) and on feature queries, never on the driver's name, and each keeps its switch:
  - Subgroup sizes (all drivers, by what the device reports; [Subgroup shaders at Turnip's 128-lane subgroups](../docs/reference/shaders.md#subgroup-shaders-at-turnips-128-lane-subgroups)): Turnip's fragment and compute subgroup shaders are pinned to the library's 64 lanes, its vertex and tessellation stages too where it allows, and its geometry stage runs one-lane subgroups (`VK_DRIVER_ID_MESA_TURNIP`; `DM_VK_SUBGROUP_GS=1` undoes it). `DM_VK_SUBGROUP_PIN` 0 / 1 / stage mask. Qualcomm's driver: unchanged.
  - Compute subgroup shuffles ([Ampere HMMA and warp shuffles of agl's upscaler on Adreno](../docs/reference/shaders.md#ampere-hmma-and-warp-shuffles-of-agls-upscaler-on-adreno)): on Turnip, compute pipelines take the library's module with its shuffles through workgroup memory (ir3 makes each index shuffle a loop); `DM_VK_SHUFFLE_LDS` 0 / 1 (restart). Qualcomm's driver: the shuffle instruction.
  - The GPU clock floor (`DM_VK_GPU_FLOOR`): through `VK_QCOM_queue_perf_hint` on Qualcomm's driver; on every other driver (Turnip) through the ADPF session, which reports each frame's span and GPU time against the game's shortest period (`DM_VK_GPU_FLOOR_ADPF`, since 2026-11-05; [A GPU clock floor that follows the present period](../docs/reference/frame-rate.md#a-gpu-clock-floor-that-follows-the-present-period-holds-a-dynamic-interval-at-its-slowest)).
  - The placed-map pre-fault (`vka_mem.c`), the geometry shader claim (`DM_VK_GS_CLAIM`), the UBWC format lists (`DM_VK_UBWC`) and the pass splits (`DM_VK_CHUNK_PASS`) stay on for every driver: not yet measured on Turnip (open). `DM_VK_PREFAULT=0` skips the pre-fault, a diagnostic for that measurement (with `DM_VK_NANSCAN=1`'s placed memory test).
- **Results** on the Honor PNM-N49 (Adreno 840), DKB's first level, fastboot runs, CPU caps 3.63 / 4.61 GHz (2026-11-02, build 3ee6e248):

### GPUs other than Adreno (Mali and others)

Untested: no Mali, Xclipse or PowerVR device has run the host. A survey of `dm/gfx/vk_android` for what such a GPU meets, in the order a game would meet it (asked for in GitHub discussion 31: a Dimensity 8400, sound but a black screen):

1. **Placed memory maps** (the first and hardest): without `VK_EXT_map_memory_placed` (or a driver that places maps without advertising it, which `vka_placed_probe` in `vka_dev.c` finds on any driver with `vkMapMemory2`: one small allocation mapped at a reserved address, kept only when it lands there), the GPU sees none of the game's memory and draws are off (`vka_draw.c`): the game runs with sound and a black screen, as reported. Whether Arm's Mali driver has placed maps is not known here; the Readiness check's report (`ext.VK_EXT_map_memory_placed`, `placed.unadvertised`) says so for a phone. Without them the host tries guest memory through exported Vulkan memory (`VK_KHR_external_memory_fd`: the memory's fd mapped over the pool's range, `vka_fd_alias.h`, `DM_VK_FD_ALIAS`; the report says `memory.fdAlias=1` when its probe passes), found to work on the Adreno 830's system driver (Forgejo PR #32); with neither, draws are off.
2. **BC textures**: `vka_tex.c` creates BC1-BC7 images in their own formats and never decodes them. Mali GPUs report `textureCompressionBC` off, so those textures cannot be made; the per-game readiness row names it. A general fix would decode BCn on the GPU (a compute pass into RGBA8 / RGBA16F images) when the feature is off: not done.
3. **Subgroups**: the shader libraries are built for 32 or 64 lanes. `sg_plan` (`vka_shader.c`) keys on the reported sizes: a Mali reporting a fixed 16 (or 4 / 8 on older ones) gets one-invocation subgroups in every stage, which is right and slower; nothing names a vendor.
4. **Per-driver defaults**: Turnip (`VK_DRIVER_ID_MESA_TURNIP`) has defaults of its own (`DM_VK_SUBGROUP_GS`, `DM_VK_SHUFFLE_LDS`), and Qualcomm's own driver (`VK_DRIVER_ID_QUALCOMM_PROPRIETARY`) takes a game profile's `subgroup_one_lane` keys (`DM_VK_ONE_LANE`); Arm's driver (`VK_DRIVER_ID_ARM_PROPRIETARY`) takes the other drivers' defaults, which were tuned on Qualcomm's.
5. **Memory types**: the guest type asks for device-local, host-visible, coherent and cached memory and falls back to coherent uncached (`vka_dev.c`): correct, with slow CPU reads where the GPU has no cached coherent type.
6. **Clock floor**: no `VK_QCOM_queue_perf_hint` and no `/dev/kgsl-3d0`, so the ADPF floor is used, as on Turnip (logged).
7. **Limits and features**: `maxComputeSharedMemorySize` (Mali: 32 KiB; the library keeps its modules within `DMSH_VK_SHARED_MAX`, 32 KiB, and a game's readiness row names more), `shaderFloat64` and `shaderStorageImageReadWithoutFormat` (often off on Mali), geometry and tessellation, sparse residency (degraded: dense images): each is a readiness row or a feature query, not a vendor check.
8. **Custom drivers**: libadrenotools loads Adreno drivers only. The not-ready notice no longer suggests a custom driver when the reported vendor ID is not Qualcomm's (`Readiness.customDriversFit`); the GPU driver list still offers Turnip downloads on every phone.

What would help first: a Readiness check report (Copy report) from a Mali phone, which answers 1, 2 and 7.

### The host's launcher interface

The launcher's JNI shim (`android/app/src/main/cpp/nxlaunch.c`) includes the host's own headers, [`dm/host/android/input_android.h`](../dm/host/android/input_android.h) and [`dm/gfx/vk_android/vk_android.h`](../dm/gfx/vk_android/vk_android.h), and declares every entry point weak: the signatures cannot drift apart, and a host without one still loads (the call does nothing; the log says `[nxlaunch] hooks: window …, input …, lifecycle …`). `GameActivity` and `SelftestActivity` call them through `Native`. The game runs in the process `:game`, so its window, input and lifecycle calls reach that process's `libnxhost.so`. `libnxhost.so`'s `JNI_OnLoad` looks for the optional Kotlin class `dev.nxnative.NxHost` ([PORTING.md](PORTING.md#launcher-interface)); this launcher has none, so it binds nothing and returns normally.
